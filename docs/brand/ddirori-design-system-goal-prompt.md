목표: 띠로리 음악 서비스 제품군이 실제로 가져다 쓸 수 있는 공통 디자인 시스템을 설계하고 구현한다. 악보앱에 이미 구현된 컴포넌트를 출발점으로 삼아, 공통 토큰·Flutter 컴포넌트 패키지·웹 참조 구현·실행 가능한 카탈로그·제품별 적용 지침을 완성한다. 문서와 색상표만으로 완료하지 않는다.

## 브랜드 기준

- 모브랜드는 **띠로리 / Ddirori**, 코드·경로 접두사는 `ddirori`다.
- 현재 기준은 `docs/brand/ddirori-visuals/README.md`, `palette.json`, `round-4/`의 SVG다. `palette.json`에서는 현재 `light` 값을 사용한다. `proposals`, `previousRound`, 과거 이미지의 색을 현재 기준으로 섞지 않는다.
- 대표색 `#0077C8`, 하늘색 `#A8D4E5`, 살구색 `#F3BB9B`, 잉크 `#203849`, 화면 바탕 `#F7FBFE`, 흰색 `#FFFFFF`를 유지한다. 나머지 의미별 색과 대비 계산은 현재 palette.json을 출발점으로 삼는다.
- 다크 값은 `darkProposal`에 있는 검토안이다. 실제 컴포넌트 위에서 검증하고 조정 근거를 기록한다. 다크 UI의 밝은 행동색과 앱 아이콘 대표색은 역할이 다르다.
- 음형은 **64분·64분·점32분**이다. 맨 위 선은 앞의 두 음만 연결하고, 아래 세 선은 세 음 전체를 연결한다. 오른쪽 기둥도 맨 아래까지 내려가며 마지막 음에는 점이 있다. 머리와 기둥의 접점 수정도 보존한다. 기본형과 소형 SVG를 용도에 맞게 사용한다.
- 바흐는 승인된 흰 가발·둥근 얼굴·작은 눈과 입을 유지한다. 놀란 얼굴도 앱 아이콘 후보지만 앱별 심벌 배정은 확정하지 않는다. 반복 작업 화면에서는 작은 보조 자산으로 사용한다.
- 도요·기러기의 이름·동물 로고·팔레트·로딩 동작은 현재 체계에 포함하지 않는다. 이전 디자인 시스템에서는 코드와 문서의 재사용 가능한 구조만 평가한다.
- 친근함은 둥근 형태와 표정에서 만들고, 전문 도구에서는 정보 계층·작업 밀도·명확한 조작을 우선한다. 악보 지면과 출력은 흰색·검정을 기본으로 한다.
- Figma는 변수·컴포넌트 변형·상태·레이아웃을 일관되게 운영하는 구조의 참고다. 로고·팔레트를 복제하거나 Figma 연결을 작업의 필수 조건으로 만들지 않는다.

## 진행 순서

### 1. 컴포넌트 조사와 공유 경계

기존 컴포넌트별로 실제 소스·용도·상태·입력 방식·직접 지정 스타일·도메인 의존성·개선점을 기록한다. 아래 세 층으로 나누고 각 후보에 유지·추출·합성·앱 전용 판단을 붙인다.

- 기초: 색·타입·간격·모서리·윤곽·포커스·모션·아이콘·밀도.
- 공통 UI: 버튼·입력·칩·툴바·목록·시트·다이얼로그·배너·상태·진행 표시.
- 음악 도구 패턴: 페이지 조작·주석 도구·재생 조작·BPM·음정 표시. 표시용 값과 callback을 받아 조합하며 저장소·파일·권한·오디오 서비스는 주입받는 앱 쪽에 둔다.

실제 공유할 소비처와 사용 예를 제시하고, 근거 없는 범용 옵션을 늘리지 않는다. 기존 main.dart 전체 분리나 제품 기능 재설계를 목표에 섞지 않는다.

### 2. 토큰과 화면 문법

현재 브랜드 팔레트를 입력으로 읽는 토큰 원본과 생성 경로를 정한다. 기본 색 → 역할별 의미 토큰 → 컴포넌트 변형 순서로 구성하고, Flutter·CSS·TypeScript 출력이 같은 값을 사용하게 한다. 색을 여러 파일에서 수동으로 관리하지 않는다.

- 밝은/다크, comfortable/compact 밀도를 정의한다. 모드가 바뀌어도 역할명이 유지되게 한다.
- 배경·표면·본문·보조 글자·행동·선택·입력 윤곽·포커스·성공·주의·오류·뷰어 overlay를 구분한다.
- Material 3 테마에 역할을 명시적으로 매핑한다. `ColorScheme.fromSeed`만으로 선정한 대표색·글자색이 다른 값으로 바뀌게 두지 않는다.
- 한국어 본문·도구 레이블·긴 작품명·작곡가명·숫자·BPM·시간·음정 표기의 크기와 행간을 정한다. 음악 기호 글꼴은 UI 글꼴과 분리한다.
- Pretendard와 플랫폼 글꼴의 적용·fallback·라이선스·실제 지원 포맷을 확인한다. 웹 WOFF2를 Flutter에 그대로 등록할 수 있다고 가정하지 않는다.
- compact는 시각적 밀도다. 터치 영역까지 무조건 줄이지 않는다. 모바일 조작 영역, 데스크톱 키보드·마우스, 툴팁·단축키 표시를 함께 정의한다.
- 선택·오류·음정 상태를 색만으로 전달하지 않는다. 파스텔 위에는 잉크색 글자를 쓴다. 장식용 옅은 선과 컨트롤 식별에 필요한 윤곽을 구분한다.
- 뷰어의 어두운 overlay, 사보의 성부·선택·재생 위치 색, 주석 잉크색은 브랜드 색과 별도 의미다. 브랜드 파랑으로 일괄 덮어쓰지 않는다.

### 3. 공통 컴포넌트 실제 구현

Flutter를 첫 소비 환경으로 삼아 실제 import 가능한 패키지를 만든다. 기본 위치는 `packages/ddirori_ui/`로 하고, 기존 구조와 충돌하면 근거를 남겨 같은 목적의 다른 위치를 선택한다. 앱의 private 위젯이나 앱 도메인 모델을 import하지 않는다.

최소 구현 범위는 다음과 같다. 클래스명은 설계에 맞게 정하되 공개 API와 사용 예를 문서화한다.

- 버튼·아이콘 버튼: 주요/보조/위험 행동, 선택, 비활성, 작업 중 중복 실행 방지.
- 텍스트 입력·검색: 레이블, 도움말, 오류, 지우기, 긴 입력, 외부 값 변경.
- 필터/선택 칩·세그먼트: 단일/다중 선택과 키보드 접근.
- 툴바·도구 그룹: 선택 상태, 툴팁, 좁은 폭의 overflow, compact/comfortable.
- 목록/카드 항목: 선택, 썸네일, 메타정보, 보조 행동을 slot과 callback으로 구성.
- 시트·다이얼로그·설정 행: 제목, 본문 스크롤, 취소/확인, 키보드에 가려지지 않는 행동.
- 배너·빈 상태·오류 상태: 안내와 문제의 구분, 재시도 등 복구 행동, 펼칠 수 있는 진단 정보.
- 로딩·진행: 불확정/확정, 짧은 대기/긴 작업, 상태 설명, 애니메이션 축소 모드.
- 숫자 조절·슬라이더: BPM·볼륨·굵기 등에 조합 가능한 범위·단위·단계·직접 입력.
- 음악 조작 패턴: 페이지 이동, 주석 도구, 재생 조작을 공통 기반 위에 합성한 예제. BPM/박자 및 음정 미터의 표시 컴포넌트도 실제 조작 가능한 샘플로 제공한다.

기본·hover·pressed·focus·selected·disabled·loading·error 중 해당하는 상태를 정의한다. 검색 query 동기화, 선택 변경 callback, 키보드 이벤트, 시트 닫기처럼 기존 기능을 구성하는 계약도 보존한다.

웹은 같은 토큰의 범위를 제한한 CSS와 React 참조 컴포넌트를 제공한다. 버튼·검색·도구 그룹·배너/상태 등 대표 공통 요소를 실제 구현하고, Flutter와 같은 역할·상태 이름을 사용한다. Flutter와 웹의 코드를 억지로 하나의 위젯 구현으로 합치지 않는다. 저장소 전체에 영향을 주는 전역 CSS는 추가하지 않는다.

### 4. 브랜드 자산과 모션

현재 round-4의 음형과 승인된 바흐 자산을 재사용한다. 기존 PNG나 잘못된 기보를 포함한 과거 생성 보드에서 로고를 다시 추출하지 않는다. 플랫폼별 아이콘 마스크·안전 여백과 작은 크기 사용 규칙을 기록한다.

불확정 대기에는 음형의 순차 반응 같은 절제된 띠로리 로딩을 구현한다. 축소 모션에서는 정지 심벌과 상태 문구를 제공한다. 확정 진행은 실제 값을 받으며 임의의 퍼센트를 만들지 않는다. 바흐의 짧은 반응은 빈 상태·성공 등 제한된 위치에 사용하고 공연 모드에서 집중을 방해하지 않게 한다.

새 시작음·알림음·햅틱은 용도와 기본 정책을 문서화한다. 검증되지 않은 효과음을 추가하거나 앱 진입·로딩 때 자동 재생하지 않는다. 오디오 타이밍을 UI 애니메이션 타이머에 의존시키지 않는다.

### 5. 카탈로그와 제품별 통합 예제

스크린샷만 있는 문서 대신 상태·테마·밀도를 직접 바꿀 수 있는 카탈로그를 만든다. Flutter 예제는 실제 공통 패키지를 import한다. 웹 예제도 실제 토큰과 참조 컴포넌트를 사용한다.

필수 예제:

1. 악보함: 검색·정렬·필터·최근 항목·목록/그리드·빈 상태·다중 선택.
2. 악보 보기: 악보 자리 영역과 분리된 툴바·페이지 이동·주석 도구·공연 모드·로딩/복구. 실제 PDF 렌더러를 교체하지 않는다.
3. 연습 도구: 메트로놈 BPM·박자·재생 조작, 튜너의 낮음/정확/높음·신호 없음·낮은 신뢰도. 시뮬레이션 값은 데모라고 표시한다.
4. 사보 작업 공간: 실제 Chromatics의 도구 분류·팔레트·속성 패널을 참고한 compact 예제. 선택·비활성·키보드 포커스가 작동하게 한다. 사보 기능이나 저장·렌더러를 재구현하지 않는다.
5. 제품군 확장: 플레이의 작품/녹음 항목과 재생 조작 또는 커뮤니티/공연 카드 예제로 도메인 데이터만 바꿔 같은 기반을 사용할 수 있음을 보인다.

모바일 세로·태블릿 가로·데스크톱에서 확인한다. 200% 글자 확대, 긴 한국어 제목, 키보드로만 조작, touch/mouse 차이, 다크 모드, 축소 모션을 확인한다. 작은 화면의 overflow는 접기·스크롤·대체 배치로 명시적으로 처리한다.

### 6. 검증과 제품 적용 계획

공통 패키지의 analyze와 테스트, 웹 타입/빌드 검증, 카탈로그의 실제 렌더링을 수행한다. 테스트는 상호작용 계약·접근성 상태·선택/비활성·값 동기화·레이아웃 오류에 집중하고 구현 내용을 그대로 반복하지 않는다. 정적 시안만 확인한 것을 실제 앱·하드웨어·오디오 검증으로 기록하지 않는다.

토큰 생성이 결정적이고 출력이 원본과 일치하는지 확인한다. 실제 사용하는 색 쌍의 대비를 계산하고, 대비가 부족한 상태는 토큰이나 용도를 수정한다. 실행 화면과 오류 로그를 확인해 실패를 고친다. 네이티브 환경 문제로 실행하지 못한 항목은 정확한 원인과 재현 명령을 남긴다.

제품 적용 순서는 악보함의 검색·필터·목록·배너 → 뷰어 도구 → 연습 도구 → 다른 Flutter 앱 → Chromatics로 제안하되 실제 의존성에 따라 조정한다. 각 단계에 기존 심벌/경로, 새 컴포넌트 API, 앱에 남길 adapter, 회귀 확인 항목, 되돌리는 방법을 붙인다.

기존 앱 동작·패키지 식별자·스토어 이름·버전은 이번 카탈로그 작업만으로 변경하지 않는다. 제품 앱 UI를 추가로 수정하는 범위가 명시적으로 주어진 경우에는 해당 앱의 iOS 메타데이터를 같은 작업에서 갱신하고 AGENTS.md의 검증을 따른다. 문서·공통 패키지·카탈로그만 수정했다면 제품 metadata를 불필요하게 바꾸지 않는다.

- 공통 기반을 각 제품이 도입할 수 있는 순서와 구체적인 변경 대상.

## 완료 조건

1. 공통 컴포넌트가 악보앱의 실제 구현 조사와 연결되어 있고, 추출·합성·앱 전용 경계가 문서에 남는다.
2. 선정한 파랑과 최신 음형·바흐가 현재 기준으로 유지되고, 토큰의 원본과 생성물이 일치한다.
3. Flutter 예제가 제품 소스에 의존하지 않는 공통 패키지를 실제 import하여 동작한다. 웹은 같은 의미 토큰과 실제 참조 컴포넌트를 사용한다.
4. 최소 구현 범위의 컴포넌트와 음악 도구 합성 예제가 동작한다. 문서에만 정의하고 구현을 생략한 항목을 완료로 세지 않는다.
5. 악보함·뷰어·연습·사보·다른 제품의 예제에서 같은 디자인 문법과 필요한 밀도 차이를 확인한다.
6. 밝은/다크, 작은 화면, 긴 한국어, 키보드, 글자 확대, 축소 모션의 확인 결과와 남은 문제가 기록된다.
7. 실제 수행한 검사·캡처와 미확인 기기 검증을 구분한다. 남은 결함이 있으면 영향과 다음 작업을 명확히 적는다.
8. 기존 제품의 미완료 변경을 보존하고, 카탈로그 완성을 제품 전체 이행 완료로 보고하지 않는다.

작업 중 일반적인 구현 선택은 근거를 남기고 진행한다. 사용자의 답이 꼭 필요한 전략적 충돌만 짧게 질문하고, 독립적으로 진행할 수 있는 조사·구현은 계속한다. 마지막에는 결과 위치, 실행 명령, 검증 결과, 첫 제품 도입 지점을 한국어로 간결하게 보고한다.
