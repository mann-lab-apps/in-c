# Ddirori 공통 컴포넌트 디자인 반영 목표

## 실행 지시

목표모드를 시작하거나 기존 목표를 재개해 실제 작업한다.
저장소 확인 → 구현·소비 조사 → 계약 정의 → 테스트 → 최소 구현 → 검증 → 문서화를 반복한다.
한 변경 묶음 후 위험을 재평가한다. 페이지 설계와 공통 UI 계약을 혼동하지 않는다.

## 시작과 범위

- git status/worktree/log로 현재 소스와 기존 변경을 확인한다.
- AGENTS.md, shared-baseline.md, specifications, 공통 Web/Flutter 소스와 소비 앱 adapter를 읽는다.
- product-design-r1은 페이지 설계 참고 자료다. 기존 미커밋 시안·catalog/main.tsx는 보존한다.
- 이번 대상은 공통 컴포넌트와 실행 예제·계약·테스트다. 서비스별 페이지 배치와 엔진은 변경하지 않는다.
- 대표색·런처 아이콘을 임의 확정하지 않는다. 생성 토큰은 원본 변경 없이 수동 편집하지 않는다.

## 첫 작업: 목록 행 계약

Flutter DdiroriItem은 flat/trailing을 이미 제공한다. Web Item의 동일한 표시 요구를 확인한다.
Score의 악보 열기/선택/정보, Play의 작품 열기/재생/메뉴처럼 독립 행동을 제공할 수 있어야 한다.

- Web에 기존 호출을 유지하는 flat/trailing opt-in을 추가한다.
- trailing은 제목과 나란한 보조 영역, actions는 아래에 줄바꿈되는 다중 행동 영역으로 유지한다.
- 버튼 안 버튼을 만들지 않고 열기·선택·보조 행동을 독립시킨다.
- disabled에서 모든 자식 행동의 포인터·키보드 진입을 차단한다.
- 긴 한국어·공백 없는 제목·200% 글자·좁은 화면에서도 잘림/겹침을 방지한다.
- Flutter의 기존 flat/trailing 경로는 재구현하지 않고 대응 회귀를 보강한다.
- 기존 기본 카드, List의 flat 합성, 선택 및 disabled 계약을 보존한다.

## 후속 판단

구현 목록과 실제 소비 지점을 문서화하고, 기능 없음과 native 합성/미도입을 구분한다.
ProductGlyph 최신 자산은 정본·라이선스·두 플랫폼 변환 계약 확인 후 별도 변경으로 진행한다.
서비스 헤더·검색·도크·페이지 재배치는 각 서비스 디자인 적용 작업으로 남긴다.
실제 두 소비처의 요구 없이 추상화나 도메인 모델을 공통 패키지로 옮기지 않는다.

## 검증

- Web: typecheck, 전체 package test, 개발용 compile, API snapshot/명세/토큰 생성물 검사.
- 브라우저: light/dark, compact/comfortable, 좁은 폭/200%, 키보드·disabled·선택·독립 행동 및 스크린샷.
- Flutter: analyze, 전체 package widget test. 기존 계약과 narrow/large-text 회귀 확인.
- 제품 코드를 실제 변경한 경우에만 영향받은 앱 회귀와 iOS 메타데이터 규칙을 적용한다.
- 카탈로그 검증은 제품·실기기·보조기술 검증으로 표시하지 않는다.
- git diff --check, 기존 변경 보존, 실제 수행 명령과 결과를 기록한다.

## 제한과 종료

버전 변경·릴리즈 빌드·서명·배포·push/merge를 하지 않는다.
기존 사용자 변경을 스테이징하지 않으며 커밋은 별도 지시를 따른다.
범위 완료·사용자 중단·외부 차단 시 구현/카탈로그/제품 적용을 구분해 보고한다.
