# 서비스가 확장하는 띠로리 디자인 시스템

2026-10-25 · 서비스 전용 컴포넌트 설계·구현의 현재 기준.

이 시스템은 **시각 언어와 공통 조작을 공유한다. 화면 구조와 작업 흐름은 서비스가 설계한다.** Play·Score·Studio가 같은 홈 화면, 카드 배치, 탐색 메뉴를 가져야 한다는 규칙은 없다. 기존 Product Design R1~R3는 검토용 탐색 이력이며 서비스 UX의 필수 구현 명세가 아니다. 실제 제품에 이미 반영된 동작을 이 문서만으로 되돌리지는 않는다.

## 먼저 볼 것

1. 이 문서의 고정 기준·확장 경계를 읽는다.
2. [실행 기준 화면](theme-reference/preview/catalog/theme-reference.html)에서 실제 공통 컴포넌트와 로컬 조합을 확인한다. 개발 실행은 [검증·실행 방법](theme-reference/README.md).
3. [기초 치수·타입](specifications/foundations.md), [공통 상태 계약](specifications/component-rules.md), 실제 [React API](specifications/api-react.md) / [Flutter API](specifications/api-flutter.md)를 사용한다.
4. 서비스 UX 레퍼런스와 실제 사용자 작업을 바탕으로 전용 컴포넌트를 설계한다. [설계 기록 양식](#서비스에서-남길-설계-기록)은 앱 폴더에 짧게 작성한다.

새 지침은 토큰 원본을 교체하지 않는다. 치수·역할의 정본은 [tokens.json](tokens.json), 색 원본은 [color-system.json](color-system.json), 공개 API의 사실은 패키지 소스다. 목표와 현재 구현이 다르면 이를 구분하고 사용 중인 기본값을 조용히 변경하지 않는다.

공식 자료에서 확인한 내용과 띠로리의 해석은 [근거와 적용 판단](theme-reference/references.md)에 구분했다. 당근의 주황, 카카오의 노랑, MUI의 기본 외형을 섞는 방식이 아니다.

## 고정할 것과 서비스가 결정할 것

| 항목 | 제품군 공통 기준 | 서비스의 선택 |
| --- | --- | --- |
| 정보 구조 | 제목·설명·상태·행동의 위계가 읽힌다 | 메뉴, 화면 수, 탭, 탐색, 주요 작업 순서, 패널 위치 |
| 색 | 의미 역할과 라이트·다크 매핑, 문서·주석 색의 독립성 | 실제 앨범아트·문서·파형·도구 데이터 표현. 새 색 의미는 로컬 토큰으로 명시 |
| 글자 | 본문·제목·설명·수치의 공통 역할 | 긴 제목의 줄 수·전체 보기, 도메인별 정보 우선순위 |
| 간격 | 공통 간격 척도, 컨트롤별 내부 간격 | 화면 구성, 패널 폭, 실제 콘텐츠 기반 분기점 |
| 형태 | 컨트롤10, 도구8, 카드12, 패널16, 선택 칩 pill | 행/그룹/카드 중 의미에 맞는 단위 선택 |
| 조작 | 공통 입력·버튼·선택·오버레이 계약 | 도메인 명령, 비동기 저장, 유효성 규칙, 단축키·복구 정책 |
| 밀도 | 본문 가독성·터치 영역 유지 | 편집 도구 묶음의 compact, 정보량·컬럼 |
| 브랜드 | 승인된 음형·바흐 원본, 중립 바탕, 대표색 미확정 | 빈 화면·완료·도움말에서 필요한 등장 여부 |

대표색 여섯 후보 중 하나를 서비스별로 임의 확정하지 않는다. 실행 예제의 바이올렛은 상태를 확인하기 위한 비교 후보다. 현재 임시 라임도 승인된 대표색을 뜻하지 않는다. 앱 아이콘·출시 이름 확정은 이 지침의 범위 밖이다.

## 시각 기준

### 1. 표면은 정보 단위로 선택한다

- **평평한 행:** 작품·악보·구간·파일처럼 반복 탐색하는 항목. 기본은 배경 없음 또는 `surface`, 행 간 `border` 구분선. 제목과 우측 동작을 분리한다. `Item flat` / `DdiroriItem(flat: true)`부터 검토한다.
- **속성 그룹:** 같은 대상의 필드를 함께 편집할 때만 외곽선·카드 반경12를 쓴다. 내부 필드마다 다시 카드를 씌우지 않는다.
- **카드:** 서로 독립된 미리보기·콘텐츠 묶음일 때 쓴다. 모든 제목 아래 카드가 필요한 것은 아니다.
- **떠 있는 면:** 메뉴·팝오버·모달에만 대응 elevation을 사용한다. 일반 목록과 속성 그룹은 평면이다.
- **문서·미디어 면:** 악보 종이·기보·주석·앨범아트·파형은 UI 배경과 분리한다. 다크 모드라고 원본 문서나 저장된 주석색을 자동 반전하지 않는다.

선택 항목의 면은 `selection`, 글자는 `onSelection`이다. `brand`, `selection`, `surfaceMuted`는 서로 대체할 수 없다. 상태 전달은 체크·문구·기호를 함께 사용한다.

### 2. 글자 크기보다 역할을 먼저 고른다

| 사용처 | 역할 | 크기/굵기/행높이 | 규칙 |
| --- | --- | --- | --- |
| 화면 제목 | screenTitle | 24/700/1.3 | 페이지당 주제 위계, 의미상 heading 별도 지정 |
| 섹션 제목 | sectionTitle | 20/600/1.3 | 영역의 시작 |
| 목록·그룹 제목 | itemTitle | 16/600/1.3 | 설명과 굵기로 구분 |
| 본문 | body | 16/400/1.5 | 일반 정보·읽기 |
| 보조 설명 | description | 14/400/1.5 | text를 opacity로 흐리기보다 muted 사용 |
| 필드·선택 레이블 | label | 14/500/1.4 | 같은 형태의 컨트롤은 동일 역할 |
| 버튼 | action | 16/600/1.4 | compact는 기존 컴포넌트의 14px 규칙 적용 |
| 부차 메타데이터 | caption | 12/500/1.4 | 핵심 상태·실패 설명을 이 크기로 낮추지 않음 |
| 시간·마디·BPM | numeric | 16/500/1.4 | tabular numbers, 단위를 명시 |

`display`32는 소개·큰 제목의 선택적 역할이다. 작업 도구에 남발하지 않는다. 각 역할의 tracking은 토큰 원본을 따른다. 웹은 `Text`의 variant와 `as`를 함께 정한다. Flutter는 테마 `textTheme` 또는 `ddiroriTextStyle`, heading은 `Semantics(header: true)`로 분리한다.

제목은 기본 줄바꿈한다. 줄 수를 제한해야 하면 전체 제목에 접근할 방법을 함께 만든다. 레이블·오류·필수 조작을 말줄임만으로 감추지 않는다. 본문·컨트롤 글자를 화면 폭에 맞춰 축소하지 않는다.

### 3. 간격은 관계를 드러낸다

| 관계 | 값 | 원본 |
| --- | --- | --- |
| 아이콘·아주 가까운 보조 정보 | 4 또는 8 | spacing.xs/sm |
| 선택 컨트롤의 아이콘·레이블 | 6 | control.choiceGap |
| 레이블과 필드 | 6 | layout.labelGap / control.fieldGap |
| 항목 내부 정보 | 12 | layout.itemGap |
| 행·그룹 내부 패딩 | 16 | layout.rowPadding |
| 관련 없는 섹션 | 24 / 넓은 화면32 | layout.sectionGap/sectionGapWide |
| 페이지 좌우 | 16 / 넓은 화면32 | layout.pageGutter/pageGutterWide |

2px 이동·장식 마진을 임의로 쌓아 조정하지 않는다. 별도 수치가 필요한 악보 좌표·파형 크기·편집 핸들·커버 종횡비는 도메인 치수이며 로컬 상수와 이유를 둔다. 모든 수치를 spacing 토큰에 억지로 끼워 맞추지는 않는다.

### 4. 작은 화면·밀도·입력 방식은 따로 판단한다

- 기본 comfortable48, compact32. compact는 도구·속성 묶음에 국소 적용한다. 본문과 앱 전체를 14px로 줄이는 스위치가 아니다.
- 터치 조작 영역48은 폭이나 compact 여부와 별개다. Flutter `touch:false`는 실제 정밀 포인터 작업 환경일 때만 적용한다. 웹은 coarse pointer 규칙을 유지한다.
- 600/960/1280은 공통 검토 지점이다. 실제 콘텐츠가 먼저 깨지면 그보다 이른 분기점을 서비스가 정한다. 모바일/태블릿/데스크톱 이름으로 동작을 추측하지 않는다.
- `min-width:0` / Flutter `Expanded`로 콘텐츠가 줄바꿈될 수 있게 한다. 우측 보조 동작이 제목을 밀어내면 별도 줄로 옮긴다.
- 도구는 관련 명령 단위로 줄바꿈·접기·가로 스크롤 중 선택한다. 본문 페이지 전체의 가로 스크롤로 덮지 않는다. 큰 악보 캔버스의 pan/zoom은 별도다.
- 텍스트 확대200%, 한국어·영어 긴 레이블, 320px 폭, 터치48을 확인한다. 고정 높이로 입력 오류나 다중행 제목을 잘라내지 않는다.

## 상태를 조합하는 규칙

단일 상태 스크린샷만으로 전용 컴포넌트를 완성 처리하지 않는다. 해당 상태가 없는 경우에는 N/A와 이유를 둔다.

| 상태 | 표현·동작 |
| --- | --- |
| default / hover / pressed | 중립 면 → interactionHover / interactionPressed. 주요 실행은 action 계열. 서비스가 상태별 HEX를 새로 만들지 않는다 |
| selected | selection 면 + onSelection + 체크/선택 의미. 현재 재생·키보드 포커스와 혼동하지 않음 |
| focus-visible | 기존 공통 포커스 사용. 로컬 인터랙션에는 focus2/offset2, 내용이 잘리지 않게 공간 확보 |
| selected + focus | 선택 표시 유지 + 독립된 포커스. 선택 테두리를 굵게 만들어 포커스를 대신하지 않음 |
| invalid + focus | 오류 문장·연결된 설명 유지 + 포커스 식별. 색만으로 상태 전달하지 않음 |
| disabled | 실제 실행·키보드 진입 차단, 비활성 의미 전달. opacity만 낮추고 handler 유지하지 않음 |
| readOnly | 복사·탐색 가능, 편집만 차단. disabled와 구분 |
| busy | 중복 실행 방지, 진행 설명, 실패 후 복구·재시도. 장시간 도메인 작업은 취소·진행률 정책을 서비스가 결정 |
| empty / error / unavailable | 대상·원인·다음 행동이 구분됨. 기능 미제공을 빈 데이터로 위장하지 않음 |

상태는 disabled/busy의 **동작 차단**, invalid의 **내용**, selected의 **선택 의미**, focus의 **현재 조작 위치**로 나누어 합성한다. 색상 하나로 덮어쓰는 우선순위가 아니다. 네이티브 focus와 웹 outline의 외형을 픽셀 단위로 같게 만들 필요는 없다. 접근 가능한 결과를 맞춘다.

현재 공통 구현에서 모든 조합이 완전히 같지는 않다. 예를 들어 Flutter 입력의 focusedErrorBorder는 오류색을 사용하고, 일부 공통 컴포넌트 내부 치수는 하드코딩되어 있다. 신규 로컬 CSS로 내부를 덮지 말고 재현 예제를 공통 패키지 수정으로 돌린다. 이번 작업은 제품에 연결된 기본 테마를 일괄 변경하지 않는다.

모션은 feedback120ms/panel180ms, 반복 로딩1200ms가 기준이다. reduced motion에서는 위치·회전·반복 애니메이션을 정지 대안으로 바꾼다. 필수 정보는 모션·사운드·햅틱에만 싣지 않는다. 음원 재생 엔진·템포·기보 시간값은 UI 모션 토큰이 아니다.

## 브랜드·아이콘·문체의 적용

일반 UI 아이콘은 16/18/20/24 크기 역할과 1.75 선 두께를 기준으로 시각적 무게를 맞춘다. 한 도구 묶음 안에서는 같은 아이콘 계열을 쓴다. Flutter native 아이콘과 웹 아이콘의 실제 경로를 같게 강제하지 않는다. 기보 기호는 음악 폰트·엔진의 정확도를 따른다. 일반 UI 아이콘의 선 두께로 음표를 다시 그리지 않는다.

브랜드 음형과 바흐는 승인된 자산을 사용한다. 음형을 모든 버튼의 장식으로 넣거나 서비스마다 다른 바흐를 새로 그리지 않는다. 바흐는 도움·빈 상태·완료처럼 맥락이 있을 때 사용하고, 편집·감상·연습 도구는 조용하게 유지한다. 빗금·이중선은 소개 그래픽·표지에서 검토하며 입력 경계·포커스·악보 기보에 덧씌우지 않는다.

주요 행동은 작업 영역에서 우선순위가 분명하게 보이도록 한다. 저장·삭제·도움말에 모두 채색 버튼을 쓰지 않는다. 문구는 대상과 동작을 짧게 표현한다. ‘저장’, ‘다시 시도’, ‘파일 선택’처럼 쓰고 오류·권한 문제를 농담이나 캐릭터만으로 설명하지 않는다. 바흐의 친근함과 작업 도구의 전문성을 이 방식으로 함께 유지한다.

| 서비스 | 유지해야 할 도메인 구분 | 공통 문법으로 표현할 부분 |
| --- | --- | --- |
| Play | 작품·녹음·파일, 현재 재생·선택·대기열, 실제 파일 접근 실패 | 제목·설명 위계, 선택과 포커스, 독립된 행 동작, 상태 문구 |
| Score | 문서·페이지·연습 구간, 보기·주석 모드, 편집 중·저장 실패 | 도구 선택, 페이지 수치, 입력·오류, 문서와 UI의 표면 경계 |
| Studio | 문서·선택된 악보 대상, 입력 도구·속성, 미저장·실행 취소 | 국소 compact, 속성 그룹 간격, 유효성·명령 상태, 키보드 포커스 |

같은 ‘선택색’을 사용해도 선택 대상의 의미와 실제 callback은 앱이 정의한다. 현재 재생과 파일 선택, 입력 도구 활성과 악보 객체 선택을 한 상태로 합치지 않는다. 이 표는 화면 배치나 서비스 UX 레퍼런스를 지정하지 않는다.

## 전용 컴포넌트를 만드는 절차

### 공통화할 범위

| 종류 | 위치 | 예 |
| --- | --- | --- |
| 공통 primitive/interaction | packages/ddirori_web, packages/ddirori_ui | 버튼·필드·선택·다이얼로그·상태 표시 |
| 서비스 전용 조합 | 해당 앱의 presentation/components | 작품+녹음 행, 연습 구간, 사보 속성 묶음 |
| 도메인 엔진 | 해당 앱의 domain/engine | 재생 큐·파일 권한·PDF좌표·undo/redo·사보 렌더링 |

처음부터 모든 도메인 컴포넌트를 공통 패키지에 넣지 않는다. 별개 서비스에서 같은 동작 계약이 실제 필요할 때 일반화한다. 현재 예제는 로컬 조합의 출발점이며 새 공개 API가 아니다.

1. **작업을 먼저 정의한다.** 사용자가 읽을 대상, 기본 행동, 보조 행동, 실패 후 행동과 도메인 상태를 정한다. 서비스 UX 레퍼런스는 이 결정을 위해 조사한다.
2. **슬롯을 나눈다.** root / leading / title / detail / status / actions처럼 책임을 기록한다. 전체 행 클릭과 내부 버튼을 중첩하지 않는다.
3. **공통 UI로 합성한다.** 입력·버튼·선택을 새로 그리지 않는다. 기존 API에 필요한 기능이 없으면 간극을 기록하고 공통 확장과 로컬 어댑터 중 선택한다.
4. **로컬 스타일은 테마를 상속한다.** root·layout·domain slot만 꾸민다. `.dd-button`, `.dd-input-row input` 같은 공통 내부 selector를 서비스에서 재정의하지 않는다.
5. **도메인 값을 분리한다.** 값·명령·오류는 앱이 소유한다. 컴포넌트는 표시값과 callback을 받는다. 가짜 저장 성공·임시 엔진을 제품 동작처럼 만들지 않는다.
6. **테마·입력·상태를 함께 검수한다.** 아래 매트릭스를 실제 화면에서 확인하고 남은 문제를 인계한다.

### 웹에서 테마를 소비하기

```tsx
import { Item, Text } from '@ddirori/ui';
import '@ddirori/ui/styles.css';
// 앱의 기존 .ddirori / data-theme / data-density 경계를 사용한다.
// 로컬 컴포넌트마다 light나 새로운 accent를 다시 선언하지 않는다.
function MovementRow({ title, detail, onOpen }: {
  title: string; detail: string; onOpen: () => void;
}) {
  return <div className="score-movement-row">
    <Item flat title={title} subtitle={detail} onOpen={onOpen} />
    <Text variant="caption">표시할 도메인 정보</Text>
  </div>;
}
```

```css
.ddirori .score-movement-row {
  display: grid;
  gap: var(--dd-spacing-sm);
  border-bottom: var(--dd-control-border-width) solid var(--dd-border);
  color: var(--dd-text);
}
```

외부 portal의 콘텐츠도 같은 테마 스코프 안에서 토큰을 상속하도록 한다. 공통 오버레이 API를 우선 사용한다. 로컬 `--score-*` 토큰이 필요하면 `--dd-*` 역할을 참조한다. 문서 잉크처럼 독립된 데이터 색은 의미·저장 정책을 따로 둔다.

### Flutter에서 테마를 소비하기

```dart
final colors = DdiroriStyle.of(context);
final type = Theme.of(context).textTheme;
return Padding(
  padding: EdgeInsets.all(DdiroriTokens.layout['rowPadding']!),
  child: Column(crossAxisAlignment: CrossAxisAlignment.start, children: [
    Text(title, style: type.titleSmall),
    SizedBox(height: DdiroriTokens.layout['labelGap']!),
    Text(detail, style: type.bodySmall?.copyWith(color: colors['muted'])),
  ]),
);
```

앱 root는 기존 `ddiroriTheme`를 사용한다. 로컬 컴포넌트 내부에 새 `MaterialApp`이나 기본 `ThemeData()`를 넣지 않는다. 국소 compact는 현재 brightness·accent·fontFamily·입력 방식을 유지한 테마를 사용한다. 기본 Material 필드·선택기를 쓸 때는 [네이티브 합성 지침](specifications/native-recipes.md)을 따른다. TextScaler를 끄지 않는다.

실행 가능한 전체 코드: [React 조합](../../../packages/ddirori_web/catalog/theme-recipes.tsx) · [로컬 CSS](../../../packages/ddirori_web/catalog/theme-recipes.css) · [Flutter 조합](../../../packages/ddirori_ui/example/lib/theme_recipes.dart). DOM/위젯의 차이는 허용하고 색·글자 역할·간격 관계·상태 의미를 맞춘다.

## 서비스에서 남길 설계 기록

아래 내용을 해당 앱의 컴포넌트 문서에 작성한다. 중앙 문서에 모든 서비스 화면을 복제하지 않는다.

```text
컴포넌트 / 실제 사용자 작업:
서비스 UX 레퍼런스 / 채택한 동작 / 채택하지 않은 이유:
슬롯과 정보 위계:
사용한 공통 컴포넌트·타입 역할·색 역할·간격:
도메인 전용 치수·색·상태와 이유:
입력값 / callback / 비동기·오류·취소 책임:
좁은 폭·큰 글자·터치·키보드에서의 배치와 동작:
검수 화면·플랫폼 / 미확인 환경:
공통 시스템에 되돌려야 할 간극:
```

### 인계 전 확인

- 라이트·다크 × 사용하는 강조색에서 surface/text/selection/error가 유지된다.
- 일반·긴 제목, 한영 혼합, 빈 값·최대값·오류가 레이아웃을 깨지 않는다.
- 320px·대표 데스크톱 폭과 텍스트200%에서 핵심 행동이 접근 가능하다. 캔버스와 일반 UI의 스크롤을 구분한다.
- 키보드 Tab/Shift+Tab/Enter/Space/Escape와 해당 패턴의 화살표 동작을 확인한다. 포커스 복귀와 스크린리더 의미는 해당 플랫폼에서 별도 확인한다.
- selected+focus, invalid+focus, disabled, busy의 중복 실행 차단을 확인한다. API가 지원하지 않는 상태는 현행 한계로 기록한다.
- 손그림·캐릭터·색 면·그림자는 사용자 작업에 도움이 되는 위치에만 쓴다.
- 동작 테스트 통과와 시각적 완성도 판단을 분리한다. 핵심 작업 화면의 실제 캡처를 보고 검토한다.

기존 앱의 UI를 변경할 때에는 해당 앱의 테스트와 iOS 배포 메타데이터 갱신 규칙을 함께 따른다. 이 문서와 독립 기준 예제만 추가하는 작업이 제품 화면의 검수를 대신하지 않는다.
