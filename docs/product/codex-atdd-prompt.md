# Codex ATDD Goal Prompts

작성일: 2026-07-19
관련 이슈: #393

Codex 할당량을 충분히 쓰되 사용자의 인지부하를 줄이기 위한 목표모드 프롬프트다.
일단 두 개만 사용하고, 매주 결과를 보며 조금씩 고도화한다.

## 공통 작성 원칙

- 모든 GitHub 이슈 제목, 이슈 본문, 작업 요약, 검증 결과, 후속 문서는 한글로 작성한다.
- 사용자가 5분 안에 이해할 수 있도록 짧고 쉬운 문장을 쓴다.
- 기술 용어는 필요할 때만 쓰고, 처음 나올 때는 사용자가 이해할 수 있는 말로 풀어쓴다.
- 파일 경로, 명령어, API 경로, 코드 식별자는 원문 표기를 유지한다.
- 출력은 후보, 선택 이유, 변경점, 검증 결과, 다음 행동을 눈에 들어오는 단위로 나눈다.

## 1. 이슈 생성 프롬프트

```text
목표: 이 프로젝트에서 ATDD로 처리하기 좋은 새 이슈 후보를 찾아, 사용자가 바로 등록하거나 검토할 수 있는 GitHub 이슈 초안을 작성한다.

범위:
- 현재 프로젝트 상태를 확인한다.
- 서비스 코드, site, workflow, secret, 배포 설정은 수정하지 않는다.
- 새 구현을 하지 않는다.
- 중복 이슈를 만들지 않는다.
- 대표 이슈에 흡수된 항목은 새 독립 이슈로 다시 만들지 않는다.
- 이미 구현됐거나 검증 루틴에 흡수 가능한 항목은 새 이슈가 아니라 정리 후보로 분류한다.
- 사용자가 검토할 수 있는 새 이슈 초안만 만든다.
- GitHub 이슈 제목과 본문은 한글로, 비개발자도 이해할 수 있게 작성한다.

진행:
1. 먼저 현재 open issue와 최근 closed issue를 훑어 정리 후보를 찾는다.
   - 이미 처리된 이슈
   - 너무 작은 이슈
   - 같은 원인/완료 조건을 가진 중복 이슈
   - 릴리즈 검증, quality evidence, 대표 이슈에 흡수할 수 있는 이슈
2. 새로 만들지 않아도 되는 후보는 새 이슈 초안에서 제외하고, 정리 판단을 먼저 출력한다.
3. 현재 프로젝트를 훑고 새 이슈 후보 3개를 고른다.
   - ATDD 인수 기준과 검증 기준을 만들 수 있다.
   - 사용자의 인지부하를 줄이는 작은 단위다.
   - production, secret, 결제, 배포, 외부 계정 변경이 필요하지 않다.
   - 기존 작업과 중복되지 않는다.
   - 대표 이슈, 흡수된 이슈, 최근 closed 이슈와 충돌하지 않는다.
4. 후보 3개 중 가장 좋은 1개를 선택하고 이유를 짧게 설명한다.
5. 선택한 후보를 GitHub 이슈 초안으로 작성한다.
6. 이슈 안에 ATDD 인수 기준과 실패 가능한 검증 후보를 포함한다.
7. 이슈 선정 및 해결 프롬프트가 바로 사용할 목표 문장을 만든다.

중복·흡수 확인:
- 후보마다 open issue와 최근 closed issue에서 같은 기능명, 사용자 동작, 테스트 ID,
  파일 경로, 실패 증상을 검색한다.
- 댓글이나 본문에 "대표 이슈", "흡수", "묶음 처리"가 있으면 기존 대표 이슈를
  추적 대상으로 삼고 새 이슈 초안을 만들지 않는다.
- 구현은 이미 있고 남은 일이 브라우저별 smoke, GA4 콘솔 확인, release checklist 확인뿐이면
  새 구현 이슈로 만들지 말고 #386 또는 #322 같은 검증 이슈에 흡수할지 판단한다.
- 이전 PR에서 `Related to`로만 연결된 이슈는 실제 완료 조건과 현재 검증 명령을 다시 확인한다.
  검증으로 완료가 확인되면 "완료 정리 후보"로 출력하고, 새 이슈 초안은 만들지 않는다.
- 확인한 이슈 번호와 `새 이슈`, `기존 이슈 업데이트`, `대표 이슈에 흡수` 판단을
  출력에 남긴다.

출력:
- 닫기/흡수/유지 판단이 필요한 기존 이슈
- 후보 3개와 선택 이유
- 선택한 새 이슈 후보
- GitHub 이슈 제목
- GitHub 이슈 본문 초안
- ATDD 인수 기준
- 실패 가능한 검증 기준
- 중복 확인 결과
- 이슈 선정 및 해결 프롬프트에 넘길 목표 문장
- 사용자가 5분 안에 검토할 부분

완료 조건:
- 구현 변경 없이 새 이슈 초안이 남는다.
- 새 이슈보다 기존 이슈 정리가 맞는 경우에는 정리 후보와 근거가 남는다.
- 다음 단계에서 바로 사용할 목표 문장이 있다.
- 결정이 필요한 항목은 질문으로 남긴다.
```

## 2. 이슈 선정 및 해결 프롬프트

```text
목표: 이 프로젝트의 열린 GitHub 이슈 중 인지부하가 낮고 치명적이지 않은 후보를 하나 골라 ATDD 방식으로 해결한다.

범위:
- 우선 문서, 사업/운영 기준, 진행상황 문서, 검증 기준, 작은 사용자-facing 문구처럼 위험이 낮은 작업을 고른다.
- 서비스 코드, site, workflow, secret, 배포 설정은 명시 승인 없이 수정하지 않는다.
- 범위가 커지면 구현하지 말고 이슈를 분해한다.
- closed 이슈나 대표 이슈에 흡수된 세부 이슈는 독립 완료 대상으로 삼지 않는다.
- 이미 PR이 열린 이슈는 새로 구현하지 말고 PR 상태, base branch, CI, 남은 gap을 확인한다.
- ATDD 검증 중 기존 제품 버그가 드러나면 추적성 작업으로만 완료하지 않는다.
- 작업 요약, 검증 결과, 후속 문서는 한글로 쉽게 작성한다.

브랜치 기준:
- 목표모드 앱/ATDD 작업은 `dev`를 기준으로 최신화한 뒤 개별 이슈 브랜치에서 처리한다.
- 개별 이슈 PR의 base는 `dev`다.
- 문서/콘텐츠만 바꾸는 작업은 브랜치 전략 문서 기준에 따라 `main`을 base로 삼을 수 있다.
- `dev`에 merge됐다고 `main` 릴리즈 반영 완료처럼 쓰지 않는다.

진행:
1. 현재 브랜치와 워킹트리를 확인한다.
2. 열린 GitHub 이슈 중 안전한 후보 3개를 고른다.
3. 후보마다 기존 PR, 최근 merged PR, 최근 closed issue를 확인한다.
4. 후보가 closed 상태이거나 댓글/본문에 "대표 이슈", "흡수", "묶음 처리"가 있으면
   독립 이슈로 처리하지 않고 대표 이슈를 실제 추적 대상으로 삼는다.
5. 이미 구현됐거나 verifier가 통과해 완료가 확인된 이슈는 구현하지 않는다.
   - 권한이 있으면 근거 댓글을 남기고 닫는다.
   - 권한이 없으면 근거 댓글 하나만 남기고 "닫아도 됨"으로 보고한다.
6. 반드시 가장 적절한 1개만 선택하고 이유를 짧게 설명한다.
   - 나머지 2개는 작업하지 않고 다음 후보로 남긴다.
7. `dev`를 최신화한 뒤 해당 이슈만 다루는 새 브랜치를 만든다.
8. 먼저 인수 기준을 작성한다.
9. 구현 전에 실패 가능한 검증 기준을 작성한다.
10. 최소 변경만 수행한다.
11. 관련 검증을 실행한다.
12. 검증 중 기존 제품 버그가 드러나면 같은 범위에서 해결 가능한지 판단한다.
    - 이미 열린 버그 이슈가 있으면 PR에 함께 연결한다.
    - 새 버그라면 후속 이슈 초안을 만들고 현재 PR은 부분 해결로 표시한다.
13. 변경을 수정하지 말고 독립 리뷰한다.
14. 검증이 통과하면 브랜치를 푸시한다.
15. PR을 `dev` 대상으로 만들고, closing keyword를 신중히 쓴다.
16. 연결 이슈에는 PR URL, 변경 범위, 검증 명령, 남은 gap을 댓글 하나로 남긴다.
17. 사용자가 5분 안에 볼 확인 경로를 만든다.

PR 연결 규칙:
- 완료 증거가 있는 open issue에만 `Fixes`, `Closes`, `Resolves`를 쓴다.
- closed 이슈나 대표 이슈에 흡수된 세부 이슈는 closing keyword 없이 출처로만 언급한다.
- 부분 해결, 추적성 정리, 검증 보강, 대표 이슈 일부 처리는 `Related to`를 쓴다.
- `dev`에서 검증이 끝나기 전에는 `main` 릴리즈 반영 완료처럼 쓰지 않는다.
- PR이나 이슈 상태를 바꾸기 전에 현재 GitHub 계정 권한을 확인한다.
- 권한 부족으로 이슈를 닫지 못하면 중복 댓글을 남기지 말고, 기존 정리 댓글을 수정하거나
  최신 댓글 하나만 남긴다.

출력:
- 후보 3개와 선택 이유
- 선택한 이슈/목표
- 작업하지 않고 남긴 후보 2개
- 인수 기준과 각 항목의 증거 매핑
- 검증 기준과 실패 조건
- 변경 파일
- 검증 결과
- 독립 리뷰 결과
- 브랜치 이름
- PR base branch
- 푸시/PR/머지 결과
- `dev` 반영 여부와 `main` 릴리즈 반영 여부
- 이슈 댓글/close 처리 결과와 권한 gap
- 사용자가 5분 안에 확인할 경로
- 다음 후보

완료 조건:
- 작업이 작게 끝나거나, 범위가 크면 분해 이슈/프롬프트로 전환된다.
- 한 번의 실행에서는 이슈 1개만 작업한다.
- 검증 결과가 남는다.
- 완료 주장 전에 인수 기준별 증거가 모두 채워진다.
- 각 이슈 작업은 별도 브랜치에서 완료되고, `dev` 대상 PR과 머지 결과가 남는다.
- `main` 반영은 릴리즈 후보 검증 뒤 별도 PR로만 진행한다.
- 권한 문제로 이슈 close가 불가능하면 그 사실과 남긴 정리 댓글 URL을 보고한다.
- 사용자가 직접 볼 것은 최대 3개로 제한된다.
```

## 주간 고도화

매주 한 번만 아래 질문으로 두 프롬프트를 조정한다.

```text
이번 주 ATDD 목표모드 결과를 보고 두 프롬프트를 조금만 고도화해줘.

기준:
- 내가 검토하는 데 오래 걸린 부분은 줄인다.
- 자동 선택이 잘 맞았던 조건은 유지한다.
- 범위가 커졌던 조건은 제외 조건으로 추가한다.
- 출력 형식은 더 짧고 명확하게 만든다.

출력:
- 유지할 점
- 줄일 인지부하
- 바꿀 문장
- 다음 주 실험할 작은 변경 1개
```
