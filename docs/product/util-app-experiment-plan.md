# 음악 유틸앱 실험 방향성

작성일: 2026-08-10

## 핵심 방향

음악 활동 중 IT로 해결할 수 있는 반복 문제를 작은 모바일 유틸앱으로 빠르게
만들어보고, 사용자 반응이 좋은 쪽만 구체화하는 실험형 전략으로 가자.

2026-08-16 기준으로 이 전략의 중심은 무료 웹도구가 아니라 App Store / Play Store에
출시할 무료 모바일 앱 포트폴리오다. 웹페이지는 랜딩, 소개, 피드백, 관심 등록,
개인정보 고지를 위한 보조 지면으로 둔다.

관련 외부 리서치와 유통 전략 근거는
[`docs/research/app-portfolio-distribution-research-notes.md`](../research/app-portfolio-distribution-research-notes.md)에
따로 모아둔다.

핵심 원칙은 다음과 같다.

- 광고 없이 무료로 제공한다.
- 꼭 필요한 기능만 아주 단순하게 제공한다.
- 반복 사용성이 높은 문제부터 만든다.
- 한 번에 하나를 완성하려고 하기보다, 여러 후보를 빠르게 던져보고 반응이 좋은 앱만 깊게 만든다.
- 스토어 출시를 전제로 하되, 로그인/결제/서버 저장은 첫 MVP에서 제외한다.

## 제품 철학

유틸앱은 “하나의 완성형 앱”이라기보다,
“음악 생활에서 생기는 작은 불편을 해결하는 도구들의 집합”으로 본다.

예시 문제 영역은 다음과 같다.

- 연습 중 빠르게 확인해야 하는 기능
- 악보를 넘기거나 정리하는 기능
- 공연 전 준비를 돕는 기능
- 리허설/연습/공연 상황에서 쓰는 작은 보조 도구
- 반복적으로 해야 하지만 번거로운 작업

## 실험 방식

### 1. 후보를 넓게 잡는다

초기에는 3~5개 후보를 동시에 준비한다.

예시 후보:

- 튜너
- 악보 넘기기 보조
- 메트로놈/템포 보조
- 리허설 타이머
- 세트리스트/연습 순서 정리

### 2. 각 앱은 최소 기능 MVP로 빠르게 만든다

각 앱은 다음 조건을 만족하도록 한다.

- 설치와 사용이 쉬움
- 광고 없음
- 불필요한 설정 제거
- 핵심 기능만 제공

### 3. 반응이 좋은 앱만 구체화한다

다음 지표를 보고 우선순위를 정한다.

- 설치/열기 수
- 재방문률
- 특정 기능에 대한 피드백
- “다른 기능도 있었으면 좋겠다”는 요청

### 4. in C 적합도와 optionality를 분리한다

유틸앱은 in C의 고객 비전 자체가 아니라 relevant audience를 만드는 distribution
technology로 본다. 따라서 앱 성과와 in C 적합도를 분리해 판단한다.

```text
Build -> Grow -> Test relevance -> Hold / Sell / Kill
```

| 앱 성과 | in C 적합도 | 판단 |
| --- | --- | --- |
| 높음 | 높음 | Hold, distribution 자산 |
| 높음 | 낮음 | Sell, 매각 후보 |
| 낮음 | 높음 | 개선 또는 니치 검토 |
| 낮음 | 낮음 | Kill |

초기 앱을 in C에 과도하게 종속시키지 않으면, distribution 자산으로 보유하거나 별도
앱으로 매각하는 선택지를 모두 유지할 수 있다.

### 5. 릴리즈 후 바로 실험한다

토요일 릴리즈 직후에는 한 개의 작은 앱을 먼저 만들어보고,
사용자 반응을 확인한 뒤 다음 앱으로 확장한다.

## 우선순위 기준

다음 조건이 높을수록 우선순위가 높다.

- 즉시 가치가 명확한가
- 반복 사용성이 높은가
- 구현 난도가 적당한가
- 사용자에게 “이건 정말 쓸 것 같다”는 느낌을 주는가

## 같은 레포에서 다루는 방향

같은 레포에서 다루는 것이 좋다. 다만 하나의 거대한 앱으로 묶기보다,
공통 기반을 공유하는 “작은 앱들의 묶음” 형태로 관리하는 것이 적합하다.

공통으로 공유하면 좋은 요소:

- 디자인 시스템
- 배포 파이프라인
- 공통 UI 컴포넌트
- 공통 설정/상태 관리
- 앱별 공통 로직

각 앱은 독립적으로 운영되되, 공통 인프라는 재사용하는 구조가 효율적이다.

첫 모바일 앱 후보는 `in C Click`이다. Flutter 기반 iOS/Android 앱으로 시작하고,
기존 웹 메트로놈은 보조 프로토타입으로만 본다.

## 초기 실행안

- 토요일 릴리즈 직후 1개 MVP를 만든다.
- 앱은 “작게, 빠르게, 명확하게” 출시한다.
- 반응을 보고 다음 앱을 정한다.
- 이 흐름을 반복해 제품군으로 확장한다.

## 목표

이 방향의 궁극 목표는 다음과 같다.

- 음악을 하면서 사람이 실제로 느끼는 불편을 도구로 해결한다.
- 무료이고 광고 없는 경험을 제공한다.
- 작은 앱 하나가 잘 먹히면, 그다음 앱으로 자연스럽게 연결되도록 만든다.
