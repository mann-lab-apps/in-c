# Q3 공연홍보 Concierge MVP

작성일: 2026-08-13

## 결정

Community-first MVP보다 더 앞단의 검증으로, 2026년 3분기에는 공연홍보
Concierge MVP를 먼저 실행한다.

이번 MVP에서 in C는 앱, 커뮤니티, 공연 등록 폼, 광고 대시보드가 아니다. 먼저
김재만이 직접 공연 1건 이상을 받아 홍보하고, 결과를 공연자에게 전달하는 운영
실험이다.

## 왜 전환했는가

이전 흐름은 다음과 같았다.

1. 클래식 공연 홍보가 어렵다.
2. 클래식 커뮤니티를 만든다.
3. 커뮤니티에 사람이 필요하다.
4. Chromatics, Columns, 유틸 앱, organic acquisition으로 사람을 모은다.

이 흐름은 논리적으로 연결되지만, 핵심 고객 가설을 우회할 위험이 있다. 이번
전환의 핵심은 "공연홍보가 문제라면, 먼저 공연을 받아 직접 홍보해보자"이다.

따라서 지금 검증할 질문은 커뮤니티가 자생하는지가 아니라, 공연자/기획자에게
직접 가치를 전달할 수 있는지다.

## 검증 목표

이번 MVP는 "공연 홍보 서비스를 만들 수 있는가"보다 먼저, 사람이 직접 운영했을 때
공연자/기획자가 실제 효용을 느끼는지를 확인한다. 목표는 러프하게 다음 세 가지다.

### 1. 사용자의 효용 체감

사용자가 느끼는 효용은 숫자보다 먼저 확인한다. 공연자가 결과물을 보고 "내 공연을
이해하고 대신 정리해줬다", "혼자 했으면 못 했을 일을 해줬다", "다음에도 맡기고
싶다"는 감각을 갖는지가 핵심이다.

확인할 신호:

- 공연자가 홍보를 맡기는 데 심리적 저항이 낮아지는가?
- 공연 소개, 타깃, 채널, 카피가 혼자 정리할 때보다 선명해졌다고 느끼는가?
- 결과 리포트가 단순 수치 나열이 아니라 다음 홍보 판단에 도움이 되는가?
- 결과가 크지 않아도 과정 자체를 유용하게 느끼는가?
- 다음 공연에서도 다시 이야기해보고 싶다는 반응이 있는가?

### 2. 사용자의 효용을 위한 수집 지표화

지표 수집의 목적은 대시보드를 만들기 위해서가 아니라, 사용자가 느끼는 효용을
설명하고 반복 개선하기 위해서다. 따라서 초기에는 정확한 전환 추적보다 "무엇을
했고, 어디서 어떤 반응이 있었고, 다음에는 무엇을 바꿔야 하는지"를 설명할 수 있는
수준이면 충분하다.

수집할 최소 지표:

- 채널별 실행 내역: 어디에, 언제, 어떤 소재를 배포했는가
- 소재별 반응: 어떤 문장/이미지/관점에 반응이 있었는가
- 노출/클릭/반응: 각 채널에서 확인 가능한 범위의 수치
- 문의/저장/공유/DM: 예매 전환에 가까운 정성 신호
- 비용과 투입 시간: 돈보다 먼저 사람이 얼마나 개입했는가
- 공연자 피드백: 어떤 정보가 유용했고 어떤 정보는 불필요했는가
- 다음 액션: 다음 캠페인에서 반복/중단/변경할 판단

### 3. 결과에 따른 보수적 지불의사와 금액

첫 사이클의 목표는 결제가 아니라, 결과를 본 뒤 돈을 낼 가능성이 있는지 보수적으로
확인하는 것이다. "좋았어요"가 아니라, 실제로 어떤 범위에 얼마까지 낼 수 있는지,
어떤 조건이면 돈을 내기 어려운지를 듣는다.

확인할 질문:

- 이번 결과를 보고 다음에도 맡길 의향이 있는가?
- 무료가 아니라면 어떤 부분에 돈을 낼 수 있는가?
- 같은 방식으로 다시 맡긴다면 현실적으로 얼마가 부담 없는가?
- 어떤 결과나 보장이 있어야 더 높은 금액을 낼 수 있는가?
- 돈을 내기 애매하다면 이유는 효과 부족, 예산 부족, 신뢰 부족, 측정 부족 중 무엇인가?

초기 가격 판단은 공격적으로 하지 않는다. 무료 이후 바로 큰 금액을 묻기보다,
공연자 입장에서 부담 없이 낼 수 있는 최저 구간과 돈을 내기 어려운 이유를 먼저
확인한다.

## 검증 질문

### 핵심 질문

공연자 또는 기획자는 김재만에게 공연 홍보를 맡겼을 때, 결과 리포트와 실행 과정에서
다음에도 맡길 만한 가치를 느끼는가?

### 하위 질문

- 공연자에게 "무료로 한 번 홍보해보고 결과까지 보여주겠다"고 말했을 때 공연을
  맡기는 사람이 있는가?
- 공연을 이해하고 관객 타깃, 채널, 소재를 정의할 수 있는가?
- 실제 배포 후 노출, 클릭, 문의, 예매 전환에 가까운 신호를 기록할 수 있는가?
- 공연자에게 결과 리포트를 전달했을 때 유용하다는 반응을 얻는가?
- 같은 작업 중 반복되는 판단과 수작업이 발견되는가?
- 그 반복을 나중에 소프트웨어로 바꿀 수 있는가?

## 고객

초기 고객은 "클래식을 좋아하는 불특정 사용자"가 아니다.

초기 고객은 공연을 알려야 하는 사람이다.

- 연주자
- 작은 앙상블
- 공연 기획자
- 독립 주최자
- 예산과 시간이 부족한 공연 운영자

## 첫 제안 문장

```text
공연 하나 나한테 줘봐.
무료로 한번 제대로 홍보해보고,
어디에 얼마나 노출했고 어떤 반응이 있었는지 결과까지 정리해서 보여줄게.
```

이 제안은 판매보다 도움에 가깝다. 첫 목표는 돈을 받는 것이 아니라, 실제 공연
홍보 사이클을 끝까지 완주하고 고객 반응을 얻는 것이다.

## 한 사이클의 완료 정의

첫 성공 기준은 "홍보가 잘됐다"가 아니다. 다음 과정을 끝까지 완주하면 성공으로 본다.

1. 공연 확보
2. 공연 이해
3. 타깃 정의
4. 채널 선정
5. 홍보 소재 작성
6. 실제 배포
7. 성과 측정
8. 공연자에게 결과 전달
9. 피드백 청취

CTR이 낮아도, 관객 유입이 거의 없어도, 공연자가 효과를 크게 느끼지 못해도 첫
사이클은 성공이다. 두 번째 캠페인을 어떻게 바꿔야 하는지 배우면 된다.

## 기록할 데이터

| 항목 | 설명 |
| --- | --- |
| 공연명 | 공개 가능한 공연명 |
| 공연자/주최자 | 공개 가능한 이름 또는 익명 코드 |
| 공연일 | 공연 날짜 |
| 제안 경로 | 지인, 소개, 직접 연락 등 |
| 타깃 가설 | 누구에게 보여줄지 |
| 채널 | SNS, 당근, 커뮤니티, 단체방, 블로그, 광고 등 |
| 소재 | 어떤 문장/이미지/질문을 썼는지 |
| 링크 | UTM 또는 추적 가능한 링크 |
| 노출/클릭 | 채널별 가능한 범위에서 기록 |
| 문의/예매 신호 | 확인 가능한 경우만 기록 |
| 공연자 피드백 | 다음에도 맡길 의향, 불만, 개선 요청 |
| 지불의사 | 돈을 낸다면 어떤 결과/범위에 낼 수 있는지 |
| 보수적 금액 | 부담 없이 낼 수 있는 최저 금액 구간 |
| 반복 작업 | 나중에 자동화할 수 있는 작업 |

## No-build Rule

공연홍보 1건을 끝까지 완료하기 전에는 다음을 만들지 않는다.

- 광고 대시보드
- audience graph
- 자동 타깃 추천
- 공연 등록 폼
- 커뮤니티 고도화
- 마케터용 SaaS
- 콘텐츠 자동 생성 시스템

만들어도 되는 것은 운영을 기록하고 전달하는 최소 도구뿐이다. 사용자가
자동화된 서비스처럼 신청하는 경험을 만들기 위한 가벼운 웹 접수 폼은 허용한다.
단, 뒤에서 사람이 검토하고 실행한다는 점을 숨기지 않는다.

- 캠페인 기록용 Google Sheet 또는 Notion
- 결과 리포트 템플릿
- 홍보 메시지 초안
- UTM/link 기록표
- 공연자에게 보낼 제안 DM
- 공연홍보 무료 파일럿 신청 웹 폼

## 역할 가설

이번 전환으로 필요한 협업자도 더 선명해졌다.

필요한 사람은 "제품을 같이 만들 사람"보다 먼저, 실제 공연 마케팅을 해본 사람이다.

잘 맞을 가능성이 높은 사람은 다음 질문을 자연스럽게 하는 퍼포먼스/그로스 마케터다.

- 이 공연 audience는 누구인가?
- 왜 이 소재를 쓰는가?
- Meta, 당근, 지역 커뮤니티, 지인 네트워크 중 어디가 맞는가?
- CTR이 왜 낮은가?
- 클릭 이후 예매 전환이 왜 안 되는가?
- 이 채널은 반복할 가치가 있는가?

초기 역할 분담은 다음처럼 가정한다.

1. 마케터가 판단하고 실행한다.
2. 김재만이 옆에서 판단 기준과 반복 작업을 배운다.
3. 반복되는 실행을 소프트웨어로 바꾼다.
4. 나중에는 데이터가 추천하고 사람이 승인하는 구조로 발전할 수 있다.

## 기존 MVP와의 관계

Community-first MVP는 폐기하지 않는다. 다만 지금은 한 단계 뒤의 가능성으로 둔다.

공연홍보를 직접 하다 보면 관객 반응, 질문, 후기, 공연 발견 흐름이 반복적으로
생길 수 있다. 그때의 Community는 사람을 모으기 위해 억지로 만든 장이 아니라,
홍보 과정에서 생긴 대화와 반응을 담는 공간이 된다.

Columns와 Chromatics도 당장 검증 대상이 아니다. 첫 공연홍보 사이클 전에는
콘텐츠 제품화나 사보 기능 고도화로 돌아가지 않는다.

## 대화 메모에서 보존할 판단

첨부된 GPT 대화의 핵심 판단은 다음과 같이 기록한다.

- 아이디어 자체보다 중요했던 것은 틀렸을 가능성을 인정하고, 애착 있던 해결책까지
  내려놓은 점이다.
- "Mission에는 고집스럽고 Solution에는 유연한 것"이 이번 전환의 핵심이다.
- 영업 회피처럼 보였던 것은 거절 공포보다 가치 확신 부족에 가까웠다.
- 공연홍보 제안으로 바뀌자 "이건 지인들에게 권할 수 있겠다"는 감각이 생겼다.
- Builder의 질문이 "무엇을 만들까?"에서 "이 공연을 누구에게 보여줘야 하지?"로
  바뀌었다.
- 지금 필요한 것은 아이디어 확장이 아니라 확장을 멈추는 능력이다.
- 한 달 뒤 평가를 올리는 근거는 대화가 아니라 실제 공연홍보 production log다.
- 김재만 API v0.0.1의 첫 배포물은 앱이 아니라 공연홍보 한 사이클이다.

## 다음 행동

1. 연락 가능한 공연자/기획자 10명을 적는다.
2. 그중 5명에게 무료 파일럿을 제안한다.
3. 2026년 8월 안에 공연 1건을 확보한다.
4. 공연 1건에 대해 타깃, 채널, 소재, 링크, 성과를 기록한다.
5. 공연자에게 결과 리포트를 전달한다.
6. 다음 공연도 맡길 의향이 있는지 묻는다.
