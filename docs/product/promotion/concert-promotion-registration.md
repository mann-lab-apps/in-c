# 연주회 홍보 등록 UX와 데이터 모델

## MVP 흐름

연주회 홍보 등록은 긴 단일 폼이 아니라 세 단계로 나눈다.

1. 기본 정보: 제목, 날짜와 시간, 장소, 주최자, 연락처를 입력한다.
2. 프로그램: 출연자, 작품, 짧은 소개, 예매 링크, 대표 이미지를 입력한다.
3. 노출 방식: 무료/유료 홍보, 노출 기간, 미리보기, 검수 요청을 확인한다.

사용자는 각 단계에서 임시 저장할 수 있고, 검수 요청 전에는 공개되지 않는다.

## 필수 필드

| 필드 | 설명 |
| --- | --- |
| `title` | 공연명 |
| `startsAt` | 공연 시작 일시 |
| `venueName` | 장소명 |
| `venueAddress` | 주소 또는 지역 |
| `organizerName` | 주최/주관 이름 |
| `contactEmail` | 운영자 연락용 이메일 |
| `ticketUrl` | 예매 또는 상세 정보 링크 |
| `programNote` | 관객에게 보여줄 짧은 소개 |
| `promotionType` | `free` 또는 `paid` |
| `reviewStatus` | `draft`, `submitted`, `approved`, `rejected` |

## 선택 필드

- 출연자와 역할
- 프로그램 작품 목록과 작곡가
- 가격 정보
- 대표 이미지와 대체 텍스트
- 관련 Creator, Columns, 작품 페이지 ID
- 온라인/오프라인 여부

## 무료와 유료 홍보

무료 홍보는 기본 목록 노출과 검색 가능 상태만 제공한다. 유료 홍보는 결제와
검수 통과 후 지정 placement에 추가 노출된다. 유료 홍보도 광고 표시와 노출
기간을 명확히 보여야 한다.

## 상태 모델

| 상태 | 의미 |
| --- | --- |
| `draft` | 작성 중이며 외부에 노출되지 않음 |
| `submitted` | 검수 대기 |
| `changesRequested` | 수정 요청 |
| `approved` | 공개 가능 |
| `rejected` | 공개 불가 |
| `expired` | 공연 종료 또는 노출 기간 종료 |

## 모바일 구성

모바일에서는 입력 필드를 접이식 단계로 나누고, 하단 고정 영역에는 `임시 저장`
과 `다음`만 둔다. 이미지 업로드와 프로그램 입력은 선택 입력으로 두어 첫 등록
완료까지의 부담을 낮춘다.

## 후속 구현

- #316 Supabase 구축에서 프로필 소유권, 공연 공개 상태, 관계 테이블을 먼저 확정
- `ConcertPromotion` API schema 추가
- 등록 폼 컴포넌트와 단계별 validation 구현
- 검수 요청과 반려 사유 표시
- 유료 홍보 결제 상태 연결

## Supabase 연결 전 확인

Concerts 프로토타입은 #680에서 정적 페이지로 시작한다. 비로그인 사용자에게만
`내 공연 등록하기` CTA를 노출하고 로그인 페이지로 보내는 흐름은 #681에서 별도로
처리한다. 실제 저장을 붙이기 전에는 다음 결정을 #316과 맞춘다.

- 공연 등록을 시작하는 주체가 `creators`, 별도 `profiles`, 또는 둘의 조합 중
  어디에 저장되는지 결정한다.
- 공개 공연 정보와 운영자 연락처, 결제 정보, 검수 메모를 같은 테이블에 섞지 않는다.
- 공연과 작품은 `concert_works`로 연결하고, 공연과 사람/단체는
  `creator_concerts` 또는 `profile_concerts` 같은 역할 포함 관계로 연결한다.
- `draft`, `submitted`, `approved`, `rejected`, `expired` 상태가 public read/RLS와
  어떻게 대응되는지 정의한다.
- Google 로그인은 Supabase provider 설정과 개인정보 고지 업데이트 전에는 실제
  저장 플로우로 연결하지 않는다. Kakao 로그인은 `account_email` 권한 확보 또는
  별도 구현 검토 뒤, Naver 로그인은 Custom OAuth/OIDC 검증 뒤 후속 범위로 분리한다.
